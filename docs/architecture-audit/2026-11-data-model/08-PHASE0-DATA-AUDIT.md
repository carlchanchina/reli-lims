## 8.6 Item ↔ Test Project 唯一性核对（不只凭数据推断）

| 层 | 事实 |
|---|---|
| 数据库 | `Custom Field(Item.custom_reli_test_project)`：`fieldtype=Link`、`unique=0`、`reqd=0`；`SHOW INDEX FROM tabItem` 中**无任何 custom_reli_* 列索引**（连普通索引都没有）。**无唯一约束。** |
| 代码 | `service_item()` `limit 1` 默认复用第一条；显式传 `item_code` 且项目不一致才 throw（`capability_quotation.py:50-51`）。**同项目建第二个 Item 不会被拦。** |
| 数据 | 9 个检测服务商品 / 9 个不同项目；`group by project having count>1` 为空。**当前样本恰好 1:1。** |

补充异常：9 个商品中 **4 个 `custom_reli_service_capability` 为空**（`RELI-SVC-1AB4B88CEE891919`、`-348EA31818C735F3`、`-6D46CAD4A8646287`、`-D28C20A80AE275CA`）——商品存在但**没有来源能力**，溯源断链。另有 0 个项目与商品项目不一致（现有一致）。

## 8.7 历史报价覆写风险审计

- 报价行总 32 条带能力（总报价 35 张 / 行 43 条），**全部有 `custom_reli_configuration`**（0 条缺失）。
- 三列（project/object/standard）与能力现值比对：**漂移 0 条**（含已提交 8 条）。
- 结论分两部分：
  1. **代码风险成立**：`validate()` 每次保存都用 live capability 覆盖三列（`capability_quotation.py:111-115`）；只要有人重新保存一张老报价，且该能力后来被改归类，历史单据就会静默改变。当前 0 漂移只说明"还没人触发"。
  2. **已发生污染：0**。`data/quotation_drift.csv` 仅表头，可作为基线；需要定期重跑同一条查询作为回归检查。
- 覆盖情况也暴露真实使用度：32 条报价行只落在 5 个项目（`TPR-01541` 25 条、`TPR-01440` 4 条、`TPR-01365/01391/01392` 各 1 条），**全是演示/验收客户**；报价价 0/600/1200，商品 `standard_rate` 全为 0，真实价格放在 `Item Price`（600/600/1200/1200 四条）。

## 8.8 价格与规格的真实可得性

- `Item Price` 仅 4 条（Standard Selling），`standard_rate` 9 条全 0 → **价格体系只覆盖 4 个商品**。
- 项目的 `condition_template` 字段已是**数组结构**（可存多规格），但 118/120 为 `[]`，2 个有真实结构（TPR-01391 疲劳载荷含 `hold_minutes`；TPR-01440 含 `temp_c/duration_h`）。
- 即：**复用现有字段做"一项目多规格"在结构上可行**，缺的是数据回填，不是表结构。
