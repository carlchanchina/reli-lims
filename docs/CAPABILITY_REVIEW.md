# CNAS 能力审核与发布工作流

本文说明「实验室能力中心」里能力从导入到对外可用的完整路径，以及为什么批量操作不等于免审核。
入口：工作台 → 实验室能力中心 → **能力审核台**（或「待确认能力」列表）。

## 1. 状态机

```
导入 / 手工新建
      │
      ▼
   待确认 ──审核通过──▶ 已确认 ──发布──▶ 已发布 ──停用──▶ 已停用
      ▲                  │                │               
      └───退回补充────────┘                └───停用─────────┘
```

| 状态 | 对外可见 | 可被报价/委托选用 | 谁可以推进 |
| --- | --- | --- | --- |
| 待确认 | 否 | 否 | 审核人可「审核通过 / 退回补充」 |
| 已确认 | 否 | 否 | 发布人可「发布 / 停用」 |
| 已发布 | 是（投影只带必要字段） | 是 | 发布人可「停用」 |
| 已停用 | 否 | 否 | 视为下架，保留历史引用 |

`已停用` 不删除数据，历史报价、委托、方案里引用的能力仍然可以回溯，只是不再出现在新选择列表里。

## 2. 两个角色、两次动作

| 动作 | 允许角色 | 结果 |
| --- | --- | --- |
| 审核通过 / 退回补充 | `Lab Reviewer`、`Lab Manager`、`System Manager` | 写 `reviewed_by` / `reviewed_on`，追加审核记录 |
| 发布 / 停用 | `Lab Manager`、`System Manager` | 写 `published_by` / `published_on`，追加审核记录 |

`Lab Reviewer` 只审不发，`Lab Engineer` 只读（连审核都不行）。这是有意的分权：**做技术判断的人不放行对外承诺**。
审核人点击发布会被 `PermissionError` 拦下（验收脚本 `capability_review_and_roles.py` 有对应用例）。

## 3. 筛选与批量

审核台支持四个维度组合筛选：

- 实验室（`Laboratory Profile`）
- 检测项目（`Test Project`）
- 检测依据（`Test Standard`，显示为「标准号｜标题」）
- 状态（默认 `待确认`），另有 `演示` 计数
- 关键词（匹配能力范围、适用对象、编号、证书号）

批量勾选后有三个动作：**审核通过**、**退回补充**、**发布**，另有 **停用**。

硬约束：

1. **单次上限 50 条**。超了直接报错并提示「请分组审核」，不是静默截断。
2. **必须填写处理说明**（≥4 字），写进每条能力的审核记录。
3. **发布是整批事务**：只要有一条不通过预检，本批次一条都不发布，并列出每条被拦的原因。
4. **批量审核不写 `reviewed_by` 之外的东西**，金额、价格、对外文案一律不自动生成。

## 4. 发布预检（`publish_blockers`）

每条能力发布前必须满足：

| 检查 | 不通过时的提示 |
| --- | --- |
| `status == 已确认` | 只有「已确认」的能力可以发布 |
| 有 `reviewed_by` | 尚未经过审核，不能发布 |
| `capability_scope` 非空 | 必须填写能力范围（依据条款/参数） |
| `limitation` 非空 | 必须填写限制或适用说明 |
| 有 `test_project` | 必须关联统一检测项目 |
| 有 `test_standard` | 必须关联检测依据 |

真实认可类（`accreditation_type` 为 `CNAS` / `CMA`）额外要求：

| 检查 | 说明 |
| --- | --- |
| `certificate_no` 非空 | 对外承诺必须能指回证书 |
| `scope_effective_date` 非空 | 证书换版/扩项后要能判断范围是否仍有效 |

## 5. 演示能力与真实认可范围

历史导入的 651 条能力里混有一批开发演示数据。演示数据绝不能以「已认可」的姿态出现在客户面前，
所以用两个独立标记把它们物理隔开：

- `demo_only = 1`（复选框「演示能力（非认可）」）
- `accreditation_type = 演示（非认可）`
- `certificate_no` 必须以 `DEMO` 开头

交叉校验：

| `demo_only` | `accreditation_type` | 结果 |
| --- | --- | --- |
| 1 | 演示（非认可）+ `DEMO-` 证书 | 可发布（批量时需显式勾选「本次包含演示能力」） |
| 1 | CNAS / CMA | 拒绝：演示能力不能挂真实证书类型 |
| 0 | 演示（非认可） | 拒绝：类型是演示就必须勾演示 |
| 0 | CNAS / CMA | 需证书号 + 范围生效日 |

对外投影（`get_public_capability`）会带 `demo_only` 与 `scope_effective_date`，
调用方可以据此决定是否展示，不需要再去读整张表。

**批量发布演示能力必须显式勾选**，界面上是一个单独的复选框，默认不勾。
这一条是为了防止「审完 50 条顺手点发布，把演示能力一起放出去」。

## 6. 审核留痕（`Capability Review Log`）

能力表下的子表，每次动作追加一行，永不覆盖：

| 字段 | 含义 |
| --- | --- |
| `action` | 审核通过 / 退回补充 / 发布 / 停用 |
| `from_status` → `to_status` | 前后状态，能还原出完整履历 |
| `actor` / `actor_role` | 操作人与当时实际生效的角色（不是假设的角色） |
| `at` | 时间 |
| `note` | 处理说明（与批量时填的一致） |

同一批 50 条能力会有 50 条独立记录，不是一条「批量审核了 50 条」的汇总记录。
`review_note` 字段保留最新一次意见，方便列表里直接看。

## 7. 为什么不允许"全部发布"

生产部署前有 652 条能力处于 `待确认`。如果提供「全选发布」，等于把未核对的历史导入数据
直接变成对外检测能力承诺 —— 一旦客户按这个范围送样，出的是 CNAS 报告，责任在实验室。

因此工作流层面的取舍是：

- 默认筛选就是 `待确认`，一次最多看 50 条，逼着按实验室/项目/标准切块；
- 审核和发布分两个角色，发布前还有 6 项硬校验；
- 演示能力单独一道显式确认；
- 历史数据不做任何自动迁移，开发站验收时 `待确认` 计数从 652 → 653（新增测试数据），
  **没有被批量改成 `已发布`**。这一点在 `capability_review_and_roles.py` 里有断言。

## 8. 建议的推进节奏（生产）

按实验室、再按标准分批，每批 ≤ 50 条：

1. `Lab Reviewer` 对照证书附表逐条核对能力范围、限制说明、适用产品；
2. 缺字段的先「退回补充」，由维护人补齐 `capability_scope` / `limitation` / 证书号 / 生效日；
3. 每批填一句可追溯的说明，例如「2026-11 CNAS 证书 L1234 附表 3 第 1-50 行核对无误」；
4. `Lab Manager` 分批发布，发布后随机抽 3 条在客户侧报价页确认可见且带正确证书信息；
5. 证书换版时，先把旧范围 `停用`，再导入新版重新走审核，不要直接改已发布记录。
