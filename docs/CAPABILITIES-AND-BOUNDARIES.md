## 2. 委托单、Project、Task与检测表是否重复

**当前事实：确认委托会创建Project；当前代码不会自动创建Task。** Task目前是工作台快捷入口及委托内按Project筛选的入口，不代表自动任务编排已经实现。

| 对象 | 负责的事实 | 是否保留 | 与其他表的区别 |
| --- | --- | --- | --- |
| Test Request 检测委托单 | 客户声明的样品、项目、条件、报告要求、授权、确认快照 | 保留 | 客户要求和确认依据，不等于已收样或已执行 |
| Test Request Sample 委托样品行 | 客户声明名称/型号/尺寸/数量等 | 保留子表 | 声明数量与真实收样数量可以不同，不能覆盖原始声明 |
| Test Request Item 委托项目行 | 客户要求的检测方法、标准和条件 | 保留子表 | 检测执行前的约定，确认后冻结 |
| Test Request Item Sample 委托项目样品分配 | 哪个检测项目适用哪些声明样品 | 保留子表 | 一项可多个样品、一样品可多项，不能靠名称或一个字段替代 |
| Test Request Photo 委托照片 | 声明样品照片与对应关系 | 保留子表 | 原件用Frappe私有File；此表只保留关联和说明 |
| ERPNext Project 项目 | 整单归属、客户/公司、交期和整体协同 | 复用标准表 | 不复制到新“检测项目主表” |
| ERPNext Task 任务 | 人员协同、收样跟进、方案审核、报告审核及交付节点 | 保留但按需用 | 不天然具备标准/样品/设备/结果证据及复核锁定规则 |
| Sample 样品 | 实际收样的编号、状态、数量、接收人/日期、存放与处置 | 保留 | 不是商品Item；与声明样品行通过来源关联，而非重复主数据 |
| Test Program 检测方案 | 一次检测执行的方案集合、样品范围、执行及确认状态 | 保留 | Project管理整单，方案管理具体检测安排 |
| Test Program Sample 方案样品 | 本方案实际覆盖哪些Sample | 保留子表 | 多样品方案的必要关联 |
| Test Program Item 检测项目明细 | 一个具体试验：一个执行标准、方法、条件、工程师、设备、时间、结果、结论、复核 | 保留，作为检测执行权威记录 | 与Task有人员/时间/状态字段交集，但Task不能替代试验依据和证据 |
| Test Program Item Sample 项目样品分配 | 执行项目适用于哪些已收样样品 | 保留子表 | 与委托分配分别保存“客户要求”和“实际执行”；通过来源一致性约束避免误配 |
| Test Standard 检测标准 | 标准编号、版本、名称、有效状态及文件引用 | 保留一套主数据 | 文档处理只产生候选元数据，应审核后关联/更新此标准记录，不另建竞争的标准主表 |
| Test Method 检测方法 | 低温、高温、振动等方法及默认建议 | 保留 | 方法与标准不固定一对一；商城商品是对外销售包装，方法是内部执行词汇 |
| Test Report 检测报告 | 关联方案、结论、审核批准、签发PDF与修订锁定 | 保留 | 模板生成的Generated Document只是文件生成产物，不能代替此表的业务审核和签发 |
| ERPNext Asset 资产 | 真实设备、资产及现有管理能力 | 复用 | 不新建一套重复设备资产台账 |
| Workstation 工位 | 可选场地/工位引用 | 暂不扩展、不要强制 | 实验室若不使用制造工位，不必为了流程完整而要求填写 |
| Quality Inspection 质量检验 | 可选的结构化检验结果 | 按需使用 | 暂不与每个检测项目重复录入同一套结果；需要结构化测量时先确认是否适合复用 |
| Laboratory Profile 实验室资料 | 商家提交、审核、公开的实验室介绍、能力和证书资料 | 保留 | 对外目录资料，不等于真实设备占用、已核验认可范围或检测结果 |

### 最需要防止的重复

1. 不为每个Test Program Item再维护一个同等粒度、独立变化的Task状态；那会出现一边完成、一边未完成。
2. 不把客户声明样品行直接当作已收样Sample；数量差异和实物状态必须保留。
3. 不把商城商品、检测方法和标准记录合成一个对象。一个服务可按不同标准、多个版本配置。
4. 不在文档处理、Wiki和WeKnora分别建立互相竞争的标准编号/版本权威数据。原件与正式目录归Frappe，其他都是处理、展示或检索视图。
5. 目前不需要新增“检测任务”“检测执行”“检测客户”“检测设备”等同义主表。

### 建议的Task使用方式

先只在Project下使用少量协调任务，例如“委托审核”“收样核对”“方案审核”“报告复核”“交付跟进”。Task负责负责人、期限和协作，不把检测参数/测量值复制进去。

未来若确需自动生成Task，要先定义稳定来源ID、重复生成保护、取消/退回规则和状态权威；本轮只分析，不自动开发和部署此同步。

## 3. 知识库是不是转成MD上传

**是，但当前有两条已实现的代码路径，不能混成一个按钮承诺：**

1. 原始文件 → 私有Frappe File → Incoming Document → Mac解析/OCR → 规范化结构 → Markdown → 审核后的知识发布。
2. 多份允许作为知识的资料 → Markdown来源 → Mac上的llm-wiki-compiler → Knowledge Candidate候选 → 人工批准 → 内部Wiki页面 → 发布到WeKnora。

Markdown整理保留了页码/块ID线索；引用的准确性仍需真实资料验收。原始PDF继续留在私有文件区，不应因为得到MD而删除原件。

合同、发票等业务原件不能直接变成共享知识。AI抽取需要Schema与人工审核；知识候选也需审批，批准后内容若被改动应重新复核。

**这里的内部Wiki不等于公开的Astro wiki.ntbln.com。** 目前没有证据证明“批准内部候选后，公网Wiki自动更新”已经接通。公开文章发布仍需要单独、明确的流程。

当前生产知识库为空，本次没有导入507份标准；发布接口和配置已具备，不代表真实批量编译、切块质量、检索权限和答案引用已全部验收。

## 4. 中心到底放在哪里

- **业务中心：ERPNext。** 公司、客户、委托、Project、Task、样品、检测、报告及业务权限都在这里。
- **文档治理中心：Frappe的文档处理。** 原件、版本、处理任务、候选、审核及发布记录在这里。
- **专业问答和检索引擎：WeKnora。** 不是第二套业务后台。
- **公开知识展示：Astro Wiki和主站资源中心。** 不承担私有文件授权。
- **外部情报来源：AIHOT。** 采集标准变化、法规、召回、设备与招投标线索，送入审核和后续分析，不做主数据库。
- **用户入口：ReliLab；交易中心：Mercur；连接和权限边界：Core/Bridge。** 用户不应拿到WeKnora管理密钥，也不直接依赖内部解析服务。

因此先以ERPNext和检测履约为开发主线，随后接真实知识，再接AIHOT。不是先围绕AIHOT另做一个“总后台”。

## 5. 下一步开发顺序

### 第一步：开发环境可用性与中文验收（本轮）

工作台按“业务受理 / 检测执行 / 基础资料”分组；补齐本应用DocType、字段、状态、按钮、校验提示的中文翻译。保留内部英文表名、字段名、API及状态码，不改数据契约。通用词不能被改成检测专用含义而污染ERP其他模块。

只在开发机发布、迁移和测试，不动生产。中文验收后，再由你决定生产发布时间。

### 第二步：开发机跑通一个检测履约闭环

使用明确标注的演练客户和样品，或你提供的真实业务。委托草稿→确认→Project→真实/演练收样→检测方案→项目执行→复核→报告草稿。演练不能假冒真实结果；没有真实结果和有效报告文件就不签发正式报告。

优先补必要的退回/修订、数量差异、责任人、原始记录和权限验收；确认现有角色组合可用，不再先加新表。

### 第三步：让主站和商城提交真实受理需求

先把客户请求明确接入Test Request草稿或批准的受理接口，配置最小权限和组织隔离。再核对商家/Offer/ERP Item映射、签名、幂等和失败重试，最后选择真实服务启用自动同步。不能直接打开全量同步开关。

### 第四步：用少量标准验收知识链路

先拿原分类表和3～5份有代表性的资料：核对编号/版本→解析→审核MD→发布生产知识库→查到正确条目及引用。再做标准主数据关联、更新/下架和权限测试，之后才处理全量507条。

门户用户上传、审核、独立前几页预览、全文下载授权仍需开发；ERP内部上传可用不等于这些外部功能已完成。

### 第五步：AIHOT外部情报接入

先确认实际部署URL、版本和OpenAPI，再选少量可靠信源，完成去重、来源时间、纠错、人工确认及RAG索引。主站情报页当前仍有演示内容，不能当实时采集成果。情报不自动发询价、不自动建订单。

## 6. 这轮明确不做的事

不迁移或升级生产框架；不改生产应用/数据；不新增重复业务表；不把开发库覆盖生产；不发布演练报告；不将全部PDF直接公开；不把WeKnora与AIHOT密钥放前端。

## 7. 判断“走得通”的验收标准

这条架构可行，但应以一条小闭环证明：一个客户、一份委托、一个Project、两份样品、三个检测项目、受控结果复核、一个报告草稿；再用一份标准证明解析→审核→索引→可追溯回答。每一步有真实状态和权限验证，而不是只有工作台入口或示例页面。
