# Reli LIMS V1 收口开发计划

> 目标：不再扩功能，围绕“委托 → 收样 → 试验 → 报告 → 完成”这一条主线，把现有 Reli LIMS 收紧、中文化、可视化，并完成 V1 封版。

## 1. 收口原则

1. **不新建独立前端，不再引入第二套看板系统。**
2. **ERPNext Project 继续作为正式项目执行主线。**
3. **Reli LIMS 只保留检测行业必须的 DocType。**
4. **委托单只负责“客户委托事实”，不承载全部实验室管理字段。**
5. **样品、试验方案、报告各自负责自己的生命周期。**
6. **工作台围绕业务状态，不围绕技术 DocType 平铺。**
7. **所有用户可见名称、字段、状态、Workspace、角色显示统一中文。**
8. **内部 fieldname / Python 类名可继续使用英文，避免无必要的数据迁移。**

---

## 2. V1 唯一主流程

```text
委托单
  ↓ 确认
自动创建 ERPNext Project
  ↓
收样 / 样品登记
  ↓
试验方案
  ↓
试验执行
  ↓
报告编制 / 审核
  ↓
已完成
```

工作台统一显示业务阶段：

```text
待确认 → 待收样 → 已收样 → 待试验 → 试验中 → 待报告 → 报告审核 → 已完成
```

说明：
- 这套“业务阶段”用于工作台与 Kanban。
- Sample、Test Program、Test Report 可保留自己的内部状态，但不要各自在首页形成一套并列流程。
- 首页以委托单/项目的总体阶段为主。

## 3. DocType 收紧

### 3.1 V1 保留的核心对象

#### A. 检测委托单（现 Test Request）
中文显示：**检测委托单**

职责：
- 谁委托
- 送什么样品
- 做哪些检测
- 什么时候需要
- 特殊要求
- 确认后生成 Project

不得继续承担：完整开票系统、完整报告编排、完整工程审核记录、试验执行记录。

#### B. 样品（Sample）
中文显示：**样品**

职责：
- 实物收样
- 样品编号
- 名称 / 型号 / 序列号
- 数量
- 收样时间 / 收样人
- 收样状态
- 存放位置
- 样品照片 / 附件
- 最终处置

#### C. 试验方案（现 Test Program）
中文显示：**试验方案**

职责：
- 一个 Project 的实验大纲
- 选择样品
- 多个检测项目
- 每个项目关联一个实际执行标准
- 工程师 / 设备 / 条件 / 时间
- 执行结果

#### D. 检测报告（Test Report）
中文显示：**检测报告**

职责：
- 汇总结果
- 编制人 / 审核人
- 结论
- 版本
- 最终 PDF

### 3.2 V1 基础资料

只保留真正会反复复用的基础资料：

1. **检测项目**（现 Test Method）
2. **检测标准**（Test Standard）
3. **设备**：直接复用 ERPNext Asset
4. **客户**：直接复用 ERPNext Customer
5. **项目**：直接复用 ERPNext Project
6. **任务**：直接复用 ERPNext Task，仅在需要时使用

### 3.3 不新增的“字典”

V1 不再为以下内容单独建立 DocType：
- 报告格式字典
- 样品处置字典
- 夹具来源字典
- 检测目的字典
- 判定方式字典
- 报告语言字典
- 普通状态字典

这些只用 Select 或设置项即可。

### 3.4 Test Method 的调整

“Test Method / 检测方法”这个名字容易让人误解成具体方法文件。

V1 用户显示统一改为：**检测项目**。

例如：
- 高温试验
- 低温试验
- 温度循环
- 湿热试验
- 振动试验
- 冲击试验
- 跌落试验
- 盐雾试验
- IP 防护

字段收紧为：
- 检测项目名称
- 分类
- 默认标准（可选）
- 默认设备（可选）
- 默认条件（可选）
- 启用
- 备注

`default_workstation` V1 暂不作为必需字段；如果现场没有实际使用 ERPNext Workstation，隐藏或移除。

### 3.5 Test Standard 的调整

中文显示：**检测标准**。

保留：
- 标准号
- 标准名称
- 版本/年份
- 状态
- 实施日期
- 标准文件
- 备注

`full_name` 保持自动生成即可，不让用户重复输入。

状态统一中文：
- 现行
- 作废/替代
- 草稿

## 4. 检测委托单大幅简化

现有 Test Request 字段过多。V1 改为四块即可。

### 第一块：基本信息

保留：
- 委托名称
- 委托日期
- 要求完成日期
- 客户
- 联系人
- 联系电话
- 联系邮箱（非必填）
- 备注

`Company` 是内部 ERPNext 公司，不应作为普通委托人员重点填写；可自动取当前公司或移到系统字段。

### 第二块：样品信息

子表保留：
- 样品名称
- 型号
- 序列号（可选）
- 数量
- 外形尺寸（可选）
- 重量（可选）
- 客户样品编号（可选）
- 备注

样品照片不需要单独设计复杂业务逻辑，优先使用 Frappe Attachment；如果需要与样品行精确对应，再保留最小图片子表。

### 第三块：检测项目

子表保留：
- 检测项目
- 检测标准
- 适用样品
- 试验条件/客户要求
- 备注

“一个检测项目对应一个本次执行标准”继续作为 V1 规则。

### 第四块：客户特殊要求

合并为少量字段：
- 是否需要结果判定
- 判定依据（需要判定时填写）
- 是否允许分包
- 样品处置方式
- 报告特殊要求
- 其他要求

### V1 从委托单移走/隐藏的字段

以下不要占据主表单：
- 开票抬头是否同客户
- 单独 Invoice Customer
- 报告抬头是否同客户
- Report Company
- Report Address
- 报告份数
- 报告格式的复杂选择
- Test Purpose
- Fixture Required
- Fixture Provider
- Test Sequence Notes
- Customer Confirmation Record
- Engineering Review Record

其中开票信息以后交给 ERPNext 财务/销售单据；报告抬头与报告详细要求进入报告阶段或客户默认资料；工程审核进入 Frappe Workflow/审计记录，不在委托单堆文本字段。

样品只描述真实收到的实物。

字段建议最终保留：
- 样品编号（自动）
- 检测委托单
- ERPNext Project
- 客户
- 样品名称
- 型号
- 序列号
- 数量
- 收样日期
- 收样人
- 收样状态
- 样品状态说明
- 存放位置
- 尺寸
- 重量
- 备注
- 附件

样品状态统一中文：

```text
已收样 → 试验中 → 试验完成 → 留样 → 已退回 / 已处置
```

不要让 Sample 自己成为第二套项目进度看板。

## 6. 试验方案收紧

现有 `Test Program` 保留，不再新增 Test Execution DocType。

中文显示：**试验方案**。

主表：
- 项目
- 客户（自动）
- 方案名称
- 负责人
- 计划开始
- 计划完成
- 状态
- 样品
- 检测项目明细
- 备注

状态中文：

```text
草稿 → 已批准 → 试验中 → 已完成 → 已取消
```

检测项目行状态统一：

```text
待开始 → 已就绪 → 试验中 → 已完成 → 已复核
```

### 子表简化原则

目前 `Test Program Sample`、`Test Program Item`、`Test Program Item Sample` 三层关系可以保留数据库结构，但 UI 必须隐藏技术感。

用户只看到：
1. 本方案有哪些样品
2. 有哪些检测项目
3. 每个项目适用于哪些样品

不要让用户理解“Item Sample”这种内部关系表。

## 7. 报告模块收紧

中文显示：**检测报告**。

V1 字段：
- 项目
- 委托单
- 试验方案
- 客户
- 编制人
- 审核人
- 结论
- 报告版本
- 状态
- 签发日期
- 最终报告文件
- 备注

V1 暂不单独做 `Approver` 第三层角色，除非实际业务明确需要三级签字。

报告状态收紧为：

```text
草稿 → 待审核 → 已批准 → 已签发
```

“Engineering Complete / Review / Approved / Issued / Revised”对于当前 V1 过细。

报告修订先采用版本号 + Amend / 修订记录处理，不额外把“Revised”作为日常主状态。

### 第一行：关键数字

- 待确认委托
- 待收样
- 试验中
- 待报告
- 报告待审核
- 超期

### 第二块：主流程看板

待确认

已收样
待试验
试验中

- 负责人
- 要求完成日期
- 超期标识

### 第三块：高频入口

只保留：
- 新建检测委托
- 收样
- 试验方案
- 检测报告
- 检测项目

## 11. 开发执行顺序

### Sprint A — 清理与中文化

1. Workspace 全中文化。
2. 所有核心 DocType label 中文化。
3. 所有 Select 状态中文化。
4. 所有 JS/Python 用户提示中文化。
5. 隐藏/删除无必要 Workspace shortcut。
6. 不改内部 DocType name / fieldname。

验收：普通用户进入系统后，业务主流程不出现不必要的英文。

### Sprint B — 委托单瘦身

1. 按四块重新布局 Test Request。
2. 将非 V1 字段隐藏或移除。
3. 收紧必填字段。
4. 简化样品照片处理。
5. 简化检测项目与样品关联 UI。
6. 保证确认后自动创建/关联 Project 的现有逻辑继续可用。

验收：新用户可以在 3～5 分钟内完成一张典型委托单。

### Sprint C — 样品与试验执行收紧

1. Sample 字段与状态整理。
2. Test Program 中文化与布局调整。
3. Item Sample 关系对子用户隐藏。
4. 检测项目行直接完成执行记录，不新增执行 DocType。
5. 检查一个项目多个样品、多个检测项目的完整路径。

### Sprint D — 报告收紧

1. Test Report 状态缩减为 4 个。
2. 去掉 V1 不必要的三级签批。
3. 最终 PDF 作为正式签发物。
4. 报告必须能追溯 Project / Test Request / Test Program。

### Sprint E — 工作台与 Kanban

1. Testing Center 改为“检测工作台”。
2. 添加关键 Number Cards。
3. 建立统一业务阶段字段 / 计算逻辑。
4. 配置 Frappe Kanban。
5. 卡片仅显示关键业务信息。
6. 首页只保留六个高频快捷入口。

### Sprint F — V1 封版

1. 从委托单跑一遍完整 E2E。
2. 测试多样品、多检测项目。
3. 测试附件、权限、审核。
4. 测试取消、退样、超期等异常路径。
5. 清理无用字段/代码/文档。
6. 更新 README 与 DATA_MODEL。
7. 增加最小自动化测试。
8. 打 V1 tag。

## 12. V1 Definition of Done

V1 只要求完成下面这一件事：

> 一个实验室人员能从“客户委托”开始，完成收样、建立 ERPNext Project、形成试验方案、分配样品和检测项目、记录试验结果、完成审核、签发检测报告，并能在检测工作台上清楚看到每一单当前处于哪个阶段。

如果一个功能不能直接支撑这条路径，V1 原则上不做。

## V1.1 实验室入驻与能力发布

复用 Laboratory Profile 承载实验室入驻资料；Capability Source 仅消费 wekona_documents 人工审核后的结构化结果，Laboratory Capability 复用 Test Method/Test Standard，经人工确认后发布。Wiki 为知识展示，Mercur 为交易投影。保持检测执行主流程不变。

交付范围：受控来源交接、幂等导入、确认/发布/取消发布、中文 Desk 入口、公共只读白名单投影、明确标记的测试 Demo、单元和 Frappe 集成测试。远程审批验证/撤销同步和外部投影写入未实现，不作为已上线能力。部署前需在独立 Frappe 测试站点 migrate 并运行集成验收。详见 [实验室能力中心](LABORATORY_CAPABILITY_CENTER.md)。
